# 02. Ядро движка

## 1. Время

- Физический шаг 20 Гц (`dt = 0.05 с`).
- Решения пересматриваются по планировщику (раздел 8), а не каждый тик.
- Задержка реакции на событие 0,15–0,45 с по `awareness` и `concentration`; концентрация падает с усталостью.
- Два тайма по 45 минут плюс добавленное время.

## 3. Физика (`physics.json`)

- Игрок: максимальная скорость 7,0–9,8 м/с по `pace`, ускорение 3–5,5 м/с² по `acceleration`, торможение около 6 м/с², радиус разворота растёт со скоростью и падает с `agility`. С мячом скорость ниже на 10–20% по `dribbling`. Режимы интенсивности: шаг, бег, спринт, расход выносливости по режиму.
- Мяч: пас по земле 10–22 м/с, удар 18–34 м/с, гравитация, квадратичное сопротивление, отскок 0,55–0,7, трение качения, снос ветром. Дождь снижает отскок и трение.
- Инварианты: скорость не выше максимальной, нет телепортаций, мяч не проходит сквозь стойки и сетку.

## 4. Модель времени прибытия (`arrival.rs`)

Главный примитив движка. Аналитическая оценка времени, за которое игрок с текущей скоростью, ускорением, максимальной скоростью и задержкой реакции достигает точки (подход Spearman и Fernández). Используется в перехвате, контроле пространства, оценке кандидатов, прессинге, распределении ролей в обороне и выходах вратаря. Константы игрока пересчитываются раз в игровую минуту. Цикл по 22 игрокам пишется так, чтобы компилятор его векторизовал.

## 5. Восприятие (`perception.rs`)

Игрок знает позиции других с шумом, растущим с расстоянием и для игроков вне поля зрения (за спиной относительно `facing`). Игрок сканирует пространство с частотой по `vision`; после сканирования шум для игроков за спиной сбрасывается. Без сканирования слабый по видению игрок не видит открывшегося партнёра за спиной.

## 6. Контроль пространства и ценность

- Сетка 21×14, раз в 0,5 с, на основе модели прибытия, логистика через таблицу.
- Для кандидата контроль уточняется локально в 3–5 точках вокруг цели.
- Ценность позиции = xT клетки (`xt_grid.json`, сетка 16×12) × контроль.

## 7. Производительность

**Бюджеты (`perf.json`, проверяются в CI на release):**
- матч без визуализатора: до 0,5 с на ядро;
- 10 000 матчей на 8 ядрах: до 15 минут;
- ноль аллокаций в цикле тика после прогрева;
- в браузере матч в реальном времени при 16× ускорении без пропуска кадров.

**Приёмы:**
1. SoA: массивы `[f32; 22]` по полям. Буферы выделяются один раз на матч. Аллокации проверяются считающим аллокатором в тесте.
2. Прямой перебор 22 игроков с векторизацией вместо пространственных структур. Сетка только для контроля пространства.
3. Таблицы вместо формул в горячем цикле: xG, xT, сигмоида, кривые отклика, квантили ошибок.
4. Квадраты расстояний, где не нужен корень; `atan2` только при необходимости.
5. `FrameSink` как generic-параметр: в пакетных прогонах no-op, компилятор удаляет код.
6. `rayon::par_iter` по матчам, общего изменяемого состояния нет.
7. Бенчмарки `criterion`: `arrival`, `pitch_control`, `candidate_eval`, `interception`, `defense_assignment`, `full_match`. CI падает при регрессии `full_match` больше 10%. Перед оптимизацией flamegraph.

## 8. Планировщик (`scheduler.rs`)

- Физика для всех каждый тик.
- Владелец мяча и игроки в радиусе 15 м: решения каждые 0,2–0,3 с.
- Остальные: каждые 0,5 с с интерполяцией цели.
- Принудительный пересчёт по событию: потеря, отскок, удар, свисток, смена намерения.
